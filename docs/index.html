What beam is

beam is a small Go CLI that keeps a repository's active source files in sync between two Macs — a Mac Studio and a MacBook, say — using iCloud Drive as the transport. There's no server, no account, no network protocol beam invents: it writes into a folder under ~/Library/Mobile Documents/com~apple~CloudDocs/beam-vaults/ and lets iCloud carry it to your other machine, filtering out the heavy directories you never want synced (node_modules/, vendor/, build/, .venv/, …) via a .beamignore file.

Motivation

Switching machines mid-project is a common but annoying moment: a git commit-push-pull round trip for work you don't want committed yet, a full re-clone, or a slow drag-and-drop copy of a folder that includes node_modules/ and chokes iCloud (or your patience) in the process.

iCloud Drive is already there, already paid for, and already running on every Mac you own. beam's premise is that it's a perfectly good sync transport for source code — the piece actually missing is which files to sync and how to sync them safely without iCloud uploading a half-written file if something's interrupted mid-copy. That's what beam adds: an ignore file like .gitignore, and an atomic stage-and-swap so a push is never half-finished from the other machine's point of view.

No server to run

iCloud Drive is the whole transport. Nothing to host, nothing to pay for beyond iCloud itself.

Atomic by design

Push stages into a temp folder, then swaps it into place with one rename. An interrupted push can't half-write the vault.

Ignore rules that matter

Gitignore syntax, directories pruned before they're even walked — node_modules never gets touched.

Install

brew tap jayprio/beam
brew install beam

Installs a prebuilt binary — no Go toolchain required. See jayprio/homebrew-beam.

Quick start

First machine

cd /path/to/project
beam init
beam push

init prints the project's id (e.g. a6213d80) — you'll need it on the second machine.

Second machine

mkdir -p /path/to/project && cd /path/to/project
beam init --join a6213d80   # or just `beam init --join` for an arrow-key picker
beam pull

From then on, beam push / beam pull on either machine.

Commands

beam init

Scans the current directory, writes a default .beamignore (unless one already exists), creates .beam/ with a project id, and provisions a matching vault folder in iCloud Drive at beam-vaults/<name>-<id>/. Re-running init is a no-op unless --force is given.

flageffect
--join <id>attach to an existing vault instead of creating a new one
--join (no value)pick a project from an arrow-key list of everything registered in iCloud
--name <name>override the project name (defaults to the directory's basename)
--forcere-provision even if this directory is already a beam project
--force-ignoreoverwrite an existing .beamignore with beam's defaults

beam push

Copies every file not matched by .beamignore into the vault, using an atomic stage-and-swap: files are copied into a fresh staging directory first, then swapped into place with a single directory rename — so if push is interrupted, the vault is never left half written.

flageffect
--dry-runshow what push would do, write nothing
--forceclear a stale push lock before starting (doesn't override an actively-running push)
--verboseprint every add/update action, not just the summary

beam pull

Reads the vault and merges new/updated files into the local repo. Pull never deletes local files, and always respects .beamignore. A file changed on both sides since the last sync is a conflict: by default it's left alone (and reported), so nothing gets overwritten silently.

flageffect
--dry-runshow what pull would do, write nothing
--forceoverwrite local files on conflict — vault wins
--prefer-localexplicit alias for the default: skip conflicts, keep local
--verboseprint every add/update action, not just the summary

beam list

Lists every project registered in iCloud — name, id, who created it, and when each machine last pushed/pulled it.

How it works

  • .beamignore — standard gitignore syntax (wildcards, **, ! negation). Defaults exclude .git/, node_modules/, .venv/, vendor/, build/, dist/, __pycache__/, and similar. .beam/ and .DS_Store/AppleDouble files are always excluded, regardless of .beamignore's contents.
  • .beam/ (local, per-machine, never synced) — config.json (project id, vault path), manifest.json (last-known-synced file state, used to diff on the next push/pull), push.lock (advisory lock held during a push).
  • The registry — a small SQLite index at beam-vaults/registry.db, inside iCloud Drive, so it syncs to every machine automatically. It powers beam list and the --join picker, and tracks each project's last push/pull activity. Every write rebuilds the index into a temp copy and atomically renames it over the live file, so a concurrent iCloud sync can't corrupt it. If it's ever missing or unreadable, --join <id> falls back to scanning each vault's own vault-meta.json.
  • Conflicts are never auto-merged — beam syncs files, it doesn't merge them. A conflicting file is left alone until you resolve it (edit, then push or pull again) or explicitly choose --force.

Exit codes

codemeaning
0success
1fatal error, operation aborted
2completed, but with per-file errors
3pull found conflicts, left unresolved

Known limitations

  • Two machines pushing at the exact same moment isn't coordinated — there's no distributed lock over iCloud, only a local advisory lock per machine. Last push wins.
  • No automatic merge on conflicting files; you resolve them by hand.
  • macOS only (relies on iCloud Drive's local path and dataless-file behavior).
